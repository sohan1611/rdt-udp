3 · Concepts you must master

3.1 · How the middlebox works

  • One socket, one thread. NetEm listens on one UDP port. The first datagram from any address other than the receiver identifies the sender — which is why the sender must speak first, and why it may use any port.
  • Two independent channels. c2s impairs sender-to-receiver traffic, s2c impairs the ACKs coming back, each with its own seeded generator, so loss on data never disturbs the random sequence for ACKs.
  • A release queue. Every surviving copy is scheduled for a release time and held in a PriorityQueue. The loop sends everything due, then blocks in receive for exactly as long as the next release is away — at least 1 ms, because a timeout of 0 means forever, and at most 200 ms, so a stop request is noticed promptly.
  • A tiebreak. PriorityQueue gives no order to equal keys. Without an insertion counter, two packets with the same release time could leave in either order — reordering the model never asked for, and a run that stops being reproducible.

3.2 · The impairment model, and why exactly 10 random draws

For each datagram the channel takes ten random numbers, always, in a fixed order: loss; duplicate; corrupt; corrupt position; jitter; reorder; then corrupt, corrupt position, jitter and reorder again for a possible duplicate copy. Only then does it decide: drop it, or build the primary copy (maybe flip one bit; delay = base + uniform jitter, clamped at zero; plus the reorder penalty if chosen), and build a second copy if duplicated.

Why take ten even when the packet is dropped? Because then changing the loss rate does not shift any other decision. Two sweep cells that share a seed see the same delay and jitter for every surviving packet, so the difference between their results is caused by the variable under test and nothing else. This is the common random numbers technique, and it visibly reduces the noise between neighbouring points on a curve. ChannelTest guards it: "changing loss does not disturb the delay sequence". If you add an impairment, add its draws at the end and raise the constant — never draw conditionally.

3.3 · Reproducibility and seeds

  • java.util.Random has its algorithm written into the Java specification — a 48-bit linear congruential generator — so the same seed produces the same numbers on every JVM and machine. ThreadLocalRandom and SecureRandom make no such promise.
  • Do not pass seeds 1 to 10 straight through. java.util.Random only lightly scrambles its seed before the first step, so seeds that differ by one give noticeably similar first outputs. Have run_matrix.py derive each run's seed from its name — for instance the first 8 bytes of SHA-256 of exp1-sr-loss5-seed3, masked below 263 so Java's Long.parseLong accepts it. Same name, same seed, well spread.
  • The second direction's seed. The draft uses seed XOR 0x5DEECE66D — the very constant Random uses internally. It works, but you will be asked why that number. Keep it and explain it, or derive the second seed with new Random(seed).nextLong(), which mixes the bits and is easy to justify. Either way, keep a test proving the two directions produce different decisions.

3.4 · Corruption, delay, reordering

  • One bit flipped, anywhere in the datagram. Shaili's checksum catches every single-bit error, so "a corrupted packet never reaches the application" is a guarantee we can test. Real links corrupt in bursts; we choose the model that makes the invariant checkable, and the report should say so.
  • Reordering holds a packet back by reorderExtra, 20 ms by default, so the next one overtakes it. That only works if packets are closer together than 20 ms. A window of 32 over a 40 ms round trip spaces them about 1.25 ms apart — reordering happens. Stop-and-Wait has one packet in flight, so nothing can overtake it, which is the key prediction for Experiment 3.

3.5 · The trace, and the change it needs

One JSON line per decision, flushed every 256 lines, so a run killed mid-way loses at most 256. In your rewrite, add type and ack to every line (convention 11), read from bytes 1 and 8–11. Today the emulator reads only the seq field, and every ACK is built with seq 0, so all ACKs look identical — and Experiment 4 must know which ACK was lost. The rewrite is the cheapest moment to fix it.

When a packet is duplicated, the trace holds an extra line with action dup or dup+corrupt. That line is a copy the emulator made, not a transmission — analysis that counts transmissions must skip it.

3.6 · Calibration

A perfect channel, offered traffic at stepped rates, keeping the highest rate that still delivers 99% of packets. On Windows the ceiling was 64,000 packets per second, so the experiment budget is half that, 32,000. Now compare the load our experiments actually generate over a 40 ms round trip:

Stop-and-Wait 1 packet per round trip ≈ 25 packets/s window 32 32 per round trip ≈ 800 packets/s window 128 128 per round trip ≈ 3,200 packets/s — ten times under budget

The experiments run in WSL2, so the figure that counts is a WSL2 measurement. Java is not yet installed inside your Ubuntu — checked on 14 September — so installing it comes first on Friday 18.

3.7 · Measuring honestly

  • One transfer at a time. Parallel runs compete for CPU and distort each other's timings.
  • Run from inside WSL's own filesystem — clone into ~/rdt-udp, not /mnt/d/…. File access through /mnt is far slower and adds noise to every transfer.
  • JIT warm-up. Each run starts fresh JVMs, which begin slow. On Tue 22, run one configuration ten times and check whether goodput varies more than its confidence interval. If not, document that and move on; if so, add a discarded warm-up transfer.
  • Heap and GC. Run with -Xms512m -Xmx512m and -Xlog:gc:file=…. Only claim "no collection during timed runs" if the logs show it.
  • Failures are data. A run that times out writes a row marked failed. It is never silently skipped, so gaps in the results are visible.
  • Resumable. The matrix takes hours. run_matrix.py skips cells already in the CSV, so a crash does not mean starting again.

Write the three t values into your code rather than adding a statistics library. Note the first row: with 3 seeds the error bars are almost twice as wide as with 10. That is why Sunday 27's figures are a first pass, and why the buffer week reruns them at 10 seeds. Every figure states its n.

3.10 · How run_matrix.py should work

  1. Read the experiment's config: its fixed settings, the variable and its levels, the protocols, the seed count.
  2. For every cell and seed: choose free ports; derive the seed (3.3); start NetEm with a trace file; start the receiver; start the sender; wait, with a timeout.
  3. Take the sender's single RESULT line, parse its JSON, add the run settings, append one CSV row. On a timeout, append a failed row instead.
  4. Stop NetEm cleanly so its trace is closed and flushed.

Config format. docs/PLAN.md says YAML, which needs PyYAML installed. TOML, read with Python's built-in tomllib, or plain JSON, needs nothing. Decide on Tuesday 22 and stick to it.

3.11 · Cross-checking against Linux tc netem

Your WSL2 kernel builds netem as a loadable module (CONFIG_NET_SCH_NETEM=m) and tc is installed — checked on 14 September. The sender talks to the receiver directly on loopback, with Linux doing the impairment instead of our emulator:

sudo modprobe sch_netem
sudo tc qdisc add dev lo root netem delay 20ms loss 5%
# run the receiver on 9001 and point the sender straight at 127.0.0.1:9001 — no NetEm
sudo tc qdisc del dev lo root
Always remove the qdisc, even after a failed run. While it is active, everything on that machine's loopback is delayed and lossy. Put the del command in a trap in the script so it runs whatever happens.

On loopback each packet passes the qdisc once, so data and ACKs each get the delay and loss — the same as our --both. Expect some differences: netem's jitter reorders packets by default, and its delay distribution differs from our uniform one. Report them honestly. Try one run in the buffer week, not week 6, so any kernel surprise has time to be solved.

9 · Experiment 3 — retransmissions against reordering

QuestionHow much does packet reordering, with no loss at all, cost each protocol in retransmissions?
VariableReorder probability 0, 1, 2, 5, 10, 20%
Held fixedNo loss — so every retransmission is caused by reordering; all three protocols; window 32; 20 ms delay each way; reorderExtra 20 ms; adaptive RTO; file size as decided on Tue 22
SeedsAt least 3 per cell by Sun 27; 10 in the buffer week
MeasuredRetransmissions per 1,000 data packets, duplicate ACKs, goodput

What we expect

  • Stop-and-Wait: almost none. One packet in flight means nothing can overtake it; a held-back packet is simply late. It retransmits only if that lateness outruns its RTO.
  • Go-Back-N: many. The packets that overtake a held-back one arrive out of order and are discarded, so they are lost from the receiver's point of view, and the sender eventually resends the window.
  • Selective Repeat: few. Its receiver stores the early arrivals, so it only retransmits when a held-back packet is late enough to trigger its own timer.

If a result contradicts these predictions, that is the most interesting paragraph in the report — find out why.

  • No Co-Authored-By lines, no bot pull requests, and Dependabot stays off. The contributor list must show exactly our four names.

Other people's files

If you need a change in a file someone else owns, message them first. If it is urgent and they are unreachable, make the smallest change you can, say so in your PR, and tag them. A merge conflict in a file is resolved by that file's owner.

12 · Using AI without losing marks

Permitted by the briefNot permitted
Explaining concepts · debugging · reviewing your code · generating tests · boilerplate and plotting scripts · improving your writing Generating the core protocol implementation and submitting it as your own work

Our rule: use AI to understand your module, then type the code yourself. Two reasons, both about marks. The viva is individual and worth 5 of the 10 marks, and sir will ask you to change your code live — code you did not write is code you cannot change under pressure, and it scores zero however well it runs. And a chatbot asked for a textbook protocol gives every group roughly the same code. Another group in our year is doing P3, and the brief treats identical-looking submissions as collusion.

Uses that help

  • "Explain Karn's algorithm with a timeline where the ACK arrives just after a retransmission." Then close it and draw the timeline yourself.
  • "Here is my window check and a failing test. Why does it fail when the sequence numbers wrap?" — debugging code you wrote.
  • "Write tests for a receive buffer that must release packets in order." Tests are explicitly permitted.
  • "Quiz me on my module the way a viva examiner would." The single most useful thing it can do for you.

Uses that cost marks

  • "Write GoBackN.java." Even if you read it afterwards, you will not be able to change it live.
  • Putting AI output into a PR you cannot then explain in the review check.

Log it the same day

Whenever AI materially helped, add an entry under your role in AI-USE.md:

### 2026-09-17 — receive buffer
**What:** asked why Java's % operator goes negative for a wrapped sequence number
**Permitted under:** explaining concepts
**Mine:** the buffer design, all of the code, and the tests for the wrap case

Honest disclosure carries no penalty. Undisclosed use discovered at the viva does.

You are the only one of us with Claude Code. It runs inside the repository and can execute tests, which makes it very good at helping a teammate find why their code fails. Use it that way: explain, debug, review, write tests. Never use it to produce a teammate's module — that costs them their viva marks, and it would make your commit history look like you did everyone's work. Keep the contributor list clean too: no AI co-author lines in any commit, ever.

13 · Viva preparation

1. Why is the emulator a separate process?
  • No test-only code in the protocols; works across machines; swaps for tc netem without a code change.
2. How do you know the same seed gives the same run?
  • java.util.Random's algorithm is specified; fixed draw order; the determinism test compares full decision sequences.
  • Why seeds are derived from run names, not 1 to 10.
3. Why exactly ten random draws per packet?
  • Common random numbers: changing loss leaves every other decision unchanged, so cells differ only in the variable. Name the test that guards it.
4. Why does the release queue need a tiebreak?
  • Equal release times have no defined order in a PriorityQueue; without it the queue itself would reorder packets.
5. How do you know your curves measure the protocol, not your laptop running out of CPU?
  • The calibration method, the WSL2 ceiling, and the operating-point table showing every run an order of magnitude below it.
6. What does the 95% confidence interval mean here? Why are the 3-seed bars so wide?
  • x̄ ± t · s / √n; t is 4.303 for three runs and 2.262 for ten.
7. How is a retransmission labelled spurious?
  • Match attempts to trace lines, skipping dup copies; the fate of the previous attempt; the ACK's fate via the new type and ack fields; why Selective Repeat gives exact labels.
8. How does your emulator differ from tc netem, and what did the comparison show?
  • Uniform versus netem's jitter, default reordering, a loopback-wide effect. State the measured agreement and each difference.
9. Why corrupt exactly one bit?
  • Guaranteed detectable by the checksum, so an invariant can be tested; the trade-off against realistic burst errors.
10. Live change: add a burst-loss mode.
  • New config key; new draws appended after the existing ten; raise the draw constant; confirm the common-random-numbers test still passes.
11. Live change: make jitter normally distributed instead of uniform.
  • One line in the delay calculation, still consuming one draw; clamp at zero; which tests would notice.

Glossary

ARQAutomatic Repeat reQuest: reliability by detecting loss and retransmitting. Stop-and-Wait, Go-Back-N and Selective Repeat are three ARQ schemes.
RTTRound-trip time — data out, ACK back.
RTORetransmission timeout — how long the sender waits for an ACK before resending.
SRTT, RTTVARThe smoothed RTT and its smoothed variation, from which RTO is computed (RFC 6298).
Cumulative ACK"Everything up to n has arrived." Used by Go-Back-N.
Selective ACK"This particular packet has arrived." Used by Selective Repeat.
WindowHow many unacknowledged packets the sender may have in flight at once.
Sequence spaceThe range of sequence numbers: 2k values for k bits, wrapping back to 0.
GoodputUseful file bytes delivered per second — excluding headers and retransmissions.
ThroughputEvery byte put on the wire per second — including headers and retransmissions.
Spurious retransmissionResending a packet whose original actually arrived.
Network byte orderBig-endian: most significant byte first. ByteBuffer's default.
One's complement sumAddition where a carry out of the top bit is added back in at the bottom — the end-around carry. The basis of the Internet checksum.
SeedThe starting value for the emulator's random generator. Same seed, same decisions, on any machine.
95% confidence intervalA range around a measured mean reflecting run-to-run variation. Every data point we plot carries one.
JIT warm-upThe JVM runs code slowly at first and compiles hot paths as it goes, so the first packets of a run can be slower.
