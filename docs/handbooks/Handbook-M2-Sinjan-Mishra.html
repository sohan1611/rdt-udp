3 · Concepts you must master

3.1 · Why a timeout is a trade-off

Set the timeout too short and the sender resends packets that were never lost — spurious retransmissions, which waste the link. Set it too long and, after a real loss, the sender sits idle. Round-trip times vary from packet to packet, so any fixed value is wrong somewhere. That is the whole reason RTO is estimated.

3.2 · Which clock

Use System.nanoTime() for every timer and every RTT measurement. It is monotonic: it only moves forward. System.currentTimeMillis() is wall-clock time, which jumps when the system clock is corrected — a jump backwards gives a negative RTT. nanoTime values are only meaningful as differences, never as a time of day.

3.3 · One thread, one loop

Every protocol runs a loop like this, and your timer heap is what drives it:

  1. Ask the heap for the earliest deadline.
  2. Set the socket receive timeout to the time remaining — at least 1 ms, because setSoTimeout(0) means wait forever.
  3. Block in receive. Either a packet arrives, and you handle it (which may cancel or schedule timers), or SocketTimeoutException is thrown and you carry on.
  4. Fire every timer whose deadline has passed.
  5. Go back to step 1.

Why there is no race. Handling an ACK and firing a timeout happen on the same thread, one after the other, so there is never a moment when both run. With a separate timer thread, an ACK could arrive while that thread is halfway through a retransmission, and every piece of window state would need a lock — the exact concurrency the brief warns about.

Granularity. setSoTimeout works in milliseconds, so deadlines finer than 1 ms round up. Our round trips are tens of milliseconds, so this is fine. Calling setSoTimeout is a system call, so only call it when the value changes. The emulator's loop uses exactly this design — read NetEm.run and blockMillis to see it working.

Why not a Selector. A selector multiplexes many sockets; a protocol has one, so it would add nothing. It also failed outright on Sohan's Windows laptop, where the JDK could not create its internal loopback pipe.

3.4 · The timer heap

  • A PriorityQueue ordered by deadline, with an insertion counter as a tiebreak so timers due at the same instant fire in the order they were scheduled. Without the tiebreak the order is undefined, and runs stop being reproducible.
  • Cancelling. PriorityQueue.remove(timer) searches the whole queue — O(n). The alternative is lazy cancellation: mark the timer cancelled and simply skip it when it reaches the top — O(1) to cancel. With at most a window's worth of timers the leftover cancelled entries cost nothing. Pick one and be able to justify it.
  • Never change a deadline while the timer is in the queue. The heap does not notice, its ordering silently breaks, and timers fire late. To reschedule, cancel and add a new entry.
  • When firing: collect the expired timers first, then run their actions. An action that schedules a new timer while you are still iterating the queue will otherwise throw ConcurrentModificationException.
A naming trap you will be asked about. The class is called TimerWheel, but it is a heap. A real hashed timing wheel is a different structure — buckets by time slot, O(1) insert — used in operating system kernels and in Netty. We chose a heap because we have few timers and want exact ordering. Either say that confidently, or propose renaming it TimerHeap at the Friday call.

3.5 · Jacobson/Karels — RFC 6298

On the first RTT measurement R:

SRTT = R RTTVAR = R / 2 RTO = SRTT + max(G, 4 × RTTVAR) G = clock granularity, 1 ms here

On every later measurement — in this order, because the RTTVAR line uses the old SRTT:

RTTVAR = 3/4 × RTTVAR + 1/4 × |SRTT − R| (β = 1/4) SRTT = 7/8 × SRTT + 1/8 × R (α = 1/8) RTO = SRTT + max(G, 4 × RTTVAR)

Worked example — these exact numbers belong in your tests:

Sample R (ms)SRTTRTTVARRTO
100 (first)10050300
120102.542.5272.5
8099.687537.5249.6875
200112.226653.2031325.0391
The order trap. If you update SRTT first, the second row becomes RTTVAR 41.875 and RTO 270 instead of 272.5. A test using the table above catches it immediately. Note that the playbook lists the SRTT formula first for readability — follow the RFC's order in code.

Why 4 × RTTVAR. A timeout set at the average RTT would fire on roughly half of perfectly normal packets. Adding a multiple of the variation pushes the timeout into the tail of the distribution, so it fires on genuine loss.

Backoff. Each timeout doubles RTO, up to a cap. This stops a sender hammering a path that is dropping everything.

Floor and cap — a deliberate deviation. RFC 6298 recommends a minimum RTO of 1 second for the Internet. On our emulated 40 ms path that would stall every loss for 25 round trips and make adaptive RTO look terrible. Choose a lower floor and a cap, write both in docs/timers-design.md, and state the deviation and its reason in the report. An examiner will respect a documented deviation; an unexplained one looks like a mistake.

3.6 · Karn's algorithm

t = 0 ms send packet P RTO = 300 ms t = 300 ms timer fires, resend P RTO backs off to 600 ms t = 320 ms an ACK for P arrives Was it for the original? RTT = 320 ms Or for the retransmission? RTT = 20 ms — sixteen times smaller

The sender cannot tell. Feeding either number into the estimator corrupts it. Karn's rule: never take an RTT sample from a packet that was sent more than once. Keep the backed-off RTO, and only resume sampling from a packet that was sent exactly once and then acknowledged. In practice: record each packet's first send time and whether it was ever retransmitted, and sample only when the acknowledged packet was not.

3.7 · Go-Back-N

The sender keeps base (oldest unacknowledged) and nextSeq (next to send), with window size N.

EventSender action
Room in the window and data leftSend nextSeq and advance it. If nothing was outstanding, start the timer.
ACK n, inside the windowSet base = n + 1. If base == nextSeq, stop the timer; otherwise restart it for the new base. Take an RTT sample if Karn allows.
ACK n, below baseA duplicate — ignore it, count it in dup_acks
TimeoutResend every packet from base to nextSeq − 1, restart the timer, back off RTO
Receiver eventReceiver action
The expected packet, intactDeliver it; ACK it; expect the next one
Any other intact packetDiscard it; re-ACK the last packet delivered in order
A corrupt packetDrop it silently

The receiver keeps no buffer. That is what makes Go-Back-N simple, and it is exactly why it loses to Selective Repeat under loss: one lost packet forces everything behind it to be sent again.

3.8 · Why Go-Back-N needs W ≤ 2k − 1

With k sequence bits there are 2k numbers, and they wrap. The sender's window and the receiver's window (size 1) must never be able to overlap: W + 1 ≤ 2k.

k = 2, numbers 0 1 2 3. Illegal: W = 4 send 0 1 2 3 → all arrive and are delivered → receiver now expects 0 (a NEW packet) every ACK is lost → sender times out, resends the OLD 0 receiver accepts old 0 as new 0 → wrong data, silently Legal: W = 3 send 0 1 2 → delivered → receiver expects 3 every ACK is lost → sender resends old 0 1 2 → none is 3 → discarded, re-ACK 2 ✓

3.9 · Fixed RTO mode

--rto fixed:X sets RTO to X × base RTT (convention 7) with no estimation and no backoff — genuinely fixed, so Experiment 4 compares one clean policy against another.

9 · Experiment 4 — RTO sensitivity

This is the experiment that makes our submission distinctive. Other groups can say "adaptive RTO seemed better". We can say how many retransmissions were wasted, and why, because our emulator's trace records what really happened to every packet.

QuestionHow many retransmissions are spurious under fixed timeouts versus adaptive RTO, and what does each policy cost in completion time?
VariableRTO policy: fixed:1.2, fixed:1.5, fixed:2, fixed:3, adaptive
Held fixedSelective Repeat for labelling, Go-Back-N for completion time; window 32; 2% loss; 20 ms delay each way with 10 ms jitter — jitter is what makes a fixed timeout fire early
Seeds10 per cell
MeasuredRetransmissions, split into necessary, spurious — ACK lost, and spurious — premature timeout; completion time; goodput

How a retransmission is labelled

  1. The sender logs every transmission: sequence number and attempt number.
  2. From the emulator trace, take the sender-to-receiver DATA lines for each sequence number, in order. Skip lines whose action is dup or dup+corrupt — those are extra copies the emulator made, not transmissions.
  3. For attempt k ≥ 2 of packet s, look at what happened to attempt k − 1:
    • drop or corrupt — the earlier copy never usefully arrived, so this retransmission was necessary.
    • pass or reorder — the earlier copy arrived intact, so this one was spurious. Then check the receiver-to-sender trace: if the ACK for s was dropped or corrupted, label it spurious — ACK lost; otherwise spurious — premature timeout.
Why Selective Repeat, not Go-Back-N, for labelling. A Go-Back-N receiver discards intact packets that arrive out of order, so "the earlier copy arrived" does not mean "the earlier copy was accepted". Resending it may have been genuinely necessary. Selective Repeat buffers every intact packet, so for it the label is exact. Use Go-Back-N only for completion time and total retransmissions, and explain this choice in the report — it is a good viva answer.
This depends on convention 11. The trace only identifies ACKs once Sohan's rewrite adds type and ack to each line. Today every ACK is logged with seq 0. Check it is in place before week 6.

What we expect

  • fixed:1.2 — many premature timeouts, because 10 ms of jitter pushes many round trips past 1.2 × 40 ms.
  • fixed:3 — almost no spurious retransmissions, but slow recovery from every real loss.
  • adaptive — few spurious retransmissions and completion time near the best fixed setting. If it is not, find out why before writing it up.

Our rule: use AI to understand your module, then type the code yourself. Two reasons, both about marks. The viva is individual and worth 5 of the 10 marks, and sir will ask you to change your code live — code you did not write is code you cannot change under pressure, and it scores zero however well it runs. And a chatbot asked for a textbook protocol gives every group roughly the same code. Another group in our year is doing P3, and the brief treats identical-looking submissions as collusion.

Uses that help

13 · Viva preparation

1. How do you avoid a race between a timeout firing and an ACK arriving?
  • There is no race: both are events on one thread, handled one at a time.
  • Walk through the loop in 3.3; contrast with a timer thread needing locks.
2. Why a heap? And why is it called TimerWheel?
  • Few timers, exact ordering, O(log n) operations; your cancellation choice and its cost.
  • A real timing wheel is a bucketed O(1) structure; ours is a heap by choice.
3. Walk me through Jacobson/Karels with numbers.
  • First sample, then the update in RFC order; work the second row of the table in 3.5.
  • Why RTTVAR must use the old SRTT.
4. Why add four times RTTVAR?
  • Timing out at the mean would fire on about half of normal packets; the variance term moves the timeout into the tail.
5. What does Karn's algorithm protect against?
  • Draw the 300 ms / 320 ms timeline; the ambiguous ACK; the rule; backoff kept until a clean sample.
6. Why does Go-Back-N resend the whole window? Isn't that wasteful?
  • The receiver discards out-of-order packets, so everything after a loss must be resent anyway.
  • Yes, it is wasteful under loss — that is what Experiment 1 and 2 show, and why Selective Repeat exists.
7. Why W ≤ 2k − 1?
  • Sender window plus receiver window must fit in the sequence space. Draw the k = 2 case from 3.8.
8. Why nanoTime and not currentTimeMillis?
  • Monotonic versus wall clock; a clock correction could make an RTT negative.
9. Your minimum RTO differs from RFC 6298. Why?
  • 1 second is for the Internet; on a 40 ms path it stalls every loss for 25 round trips. State your floor.
10. Live change: shrink the window from 32 to 8 during a transfer.
  • New sends respect the new limit immediately; packets already in flight above it are simply acknowledged or resent as normal.
11. Live change: switch from adaptive to fixed RTO.
  • A ProtocolConfig value; no estimation and no backoff in fixed mode; show where the RTO is read.

Glossary

ARQAutomatic Repeat reQuest: reliability by detecting loss and retransmitting. Stop-and-Wait, Go-Back-N and Selective Repeat are three ARQ schemes.
RTTRound-trip time — data out, ACK back.
RTORetransmission timeout — how long the sender waits for an ACK before resending.
SRTT, RTTVARThe smoothed RTT and its smoothed variation, from which RTO is computed (RFC 6298).
Cumulative ACK"Everything up to n has arrived." Used by Go-Back-N.
Selective ACK"This particular packet has arrived." Used by Selective Repeat.
WindowHow many unacknowledged packets the sender may have in flight at once.
Sequence spaceThe range of sequence numbers: 2k values for k bits, wrapping back to 0.
GoodputUseful file bytes delivered per second — excluding headers and retransmissions.
ThroughputEvery byte put on the wire per second — including headers and retransmissions.
Spurious retransmissionResending a packet whose original actually arrived.
Network byte orderBig-endian: most significant byte first. ByteBuffer's default.
One's complement sumAddition where a carry out of the top bit is added back in at the bottom — the end-around carry. The basis of the Internet checksum.
SeedThe starting value for the emulator's random generator. Same seed, same decisions, on any machine.
95% confidence intervalA range around a measured mean reflecting run-to-run variation. Every data point we plot carries one.
JIT warm-upThe JVM runs code slowly at first and compiles hot paths as it goes, so the first packets of a run can be slower.
