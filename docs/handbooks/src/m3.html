3 · Concepts you must master

3.1 · The Selective Repeat sender

The window runs from send_base for N sequence numbers. Each slot in it is in one of three states: sent and waiting for its ACK, acknowledged, or not yet sent.

EventSender action
Room in the window and data leftSend the next packet and start its own timer
ACK s, inside the windowMark s acknowledged and cancel its timer. If s is send_base, slide send_base forward past every consecutive acknowledged slot — which may let new packets go out.
ACK s, outside the windowIgnore it
Timer for s firesIf s is still unacknowledged, resend only s and restart only its timer

3.2 · The Selective Repeat receiver

The receive window runs from rcv_base for N sequence numbers.

An intact packet s arrives…Receiver action
inside the windowACK s. Store it if not already stored. If s is rcv_base, deliver it and every consecutive stored packet after it, advancing rcv_base past them.
in the previous window, rcv_base − N to rcv_base − 1ACK s again, but do not store or deliver it
anywhere elseIgnore it

Why the previous window must be re-ACKed. Suppose s arrived and was delivered, but its ACK was lost. The sender still believes s is missing, so its send_base cannot move past it, and it keeps resending s. If the receiver ignores those copies, the sender never gets its ACK and the transfer deadlocks. Re-ACKing is what unblocks it.

3.3 · A worked timeline

A four-packet file, window N = 4. Packet 2 is lost. sender sends 1 2 3 4, starting four timers receiver gets 1 -> it is rcv_base: deliver 1, ACK 1, rcv_base = 2 receiver gets 3 -> early: store 3, ACK 3 receiver gets 4 -> early: store 4, ACK 4 sender ACK 1 -> send_base = 2. ACK 3, ACK 4 -> marked, their timers cancelled sender timer for 2 fires -> resend 2, and only 2 receiver gets 2 -> deliver 2, then 3 and 4 from the buffer; rcv_base = 5; ACK 2 sender ACK 2 -> send_base slides past 3 and 4 to 5. Done. Retransmissions: Selective Repeat 1 (packet 2) Go-Back-N 3 (packets 2, 3, 4)

3.4 · The window bound — the question you will be asked

With k sequence bits there are 2k numbers, and they wrap around to 0. The receiver can never tell an old packet 0 from a new packet 0 — both carry the number 0. So the two windows must never be able to overlap:

sender window + receiver window ≤ 2^k Go-Back-N: receiver window is 1 -> W + 1 ≤ 2^k -> W ≤ 2^k − 1 Selective Repeat: receiver window is W -> W + W ≤ 2^k -> W ≤ 2^(k−1)

The failure, with k = 2 — numbers 0, 1, 2, 3:

Illegal: W = 3 sender sends 0 1 2 -> all arrive and are delivered receiver window moves on to 3 0 1 every ACK is lost -> sender times out and resends its OLD packet 0 0 is inside the receiver's window -> stored as the NEW packet 0 -> later delivered as file data. Wrong bytes, and nothing reports an error. Legal: W = 2 sender sends 0 1 -> delivered -> receiver window moves on to 2 3 every ACK is lost -> sender resends old 0 0 is in the previous window (0 1) -> re-ACKed, not delivered ✓

This is why the sequence-space size must be at least 8 bits for our largest experiment window of 128. We use 32 bits, so only your wraparound tests ever get close to the limit.

3.5 · Modular arithmetic in Java — and the % trap

Every window test reduces to one quantity: how far is s ahead of the base, around the circle?

offset(s, base) = Math.floorMod(s − base, M) M = 2^k in the window offset(s, base) < N in the previous one Math.floorMod(base − s, M) is between 1 and N
Never use % for this. In Java, (1 − 3) % 4 is −2, because % keeps the sign of the left side. Math.floorMod(1 − 3, 4) is 2, which is the answer you need. This single substitution is the most common wraparound bug there is.

Check yourself with M = 8, base = 6, N = 4, so the window is {6, 7, 0, 1}:

s = 1 floorMod(1 − 6, 8) = floorMod(−5, 8) = 3 3 < 4 inside the window ✓ s = 2 floorMod(2 − 6, 8) = 4 4 is not < 4 not inside ✓ s = 4 floorMod(6 − 4, 8) = 2 2 is in 1..4 previous window {2,3,4,5} ✓

With 32-bit sequence numbers held in a long, M = 232 = 4,294,967,296 fits comfortably. Put these three operations in SeqSpace (convention 14) so the rule is written once, tested once, and used by Sinjan's Go-Back-N too.

3.6 · Designing the receive buffer

OptionForAgainst
Ring buffer of N slotsO(1) store and lookup; memory fixed at N × 1400 bytes; indexed by offset, which is already the wraparound-safe numberA little more bookkeeping for the head index
TreeMap by sequence numberVery little codeSorted by raw number, so after a wrap packet 0 sorts before 4,294,967,295 — the ordering breaks exactly where it matters

Recommendation: the ring buffer, indexed by offset from rcv_base. Because the index is computed with SeqSpace, wraparound is handled in one place. The buffer needs to: accept a packet and say whether it was new, a duplicate, previous-window or outside; hand back everything now deliverable, in order; and report the current base. Build and test it with no sockets at all.

3.7 · Per-packet timers

Each unacknowledged packet has a timer in Sinjan's TimerWheel — at most N at once. An ACK cancels one timer; a timeout resends one packet. Always check the packet is still unacknowledged when its timer fires. If the heap cancels lazily, a cancelled timer can still reach the top, and without that check you would resend a packet that was already acknowledged — which shows up as retransmissions on a perfect channel.

3.8 · ACKs and the sackCount field

Core: each ACK acknowledges one packet — the ack field holds its number and sackCount is 0 (convention 3). Week 7 stretch — SACK blocks: sackCount says how many ranges follow in the payload, each a pair of 32-bit start and end numbers. One ACK can then report everything received, which helps most when ACKs are being lost.

3.9 · The fallback, if Tuesday 22 needs it

Keep the receiver exactly as it is. On the sender, replace per-packet timers with one timer on the oldest unacknowledged packet; when it fires, resend only that packet. It is still selective and still correct. What it loses: when several packets in one window are lost, they are recovered one timeout at a time rather than in parallel. Document it as a deliberate simplification, and restore per-packet timers in week 7.

9 · Experiment 2 — goodput against window size

This is the heart of our claim: the gap between Selective Repeat and Go-Back-N should widen as the window grows.

QuestionHow does goodput change with window size for Go-Back-N and Selective Repeat, and does the gap widen?
VariableWindow 1, 2, 4, 8, 16, 32, 64, 128
Held fixedLoss 1% and 5% as two series; 1400-byte payload; 20 ms delay each way; 32-bit sequence space; file size, jitter and RTO mode as locked on Tue 22
SeedsAt least 3 per cell by Sun 27; 10 in the buffer week
Measuredgoodput_bps, retransmissions, throughput_bps

Load check. The largest window sends at most 128 packets per 40 ms round trip — about 3,200 packets a second — an order of magnitude under the harness budget, so the curves reflect the protocols, not the machine. These runs take seconds to a minute each, unlike Stop-and-Wait.

What we expect

  • At window 1, both protocols behave like Stop-and-Wait.
  • Selective Repeat's goodput keeps rising with the window.
  • Go-Back-N rises, then flattens or falls, because each loss can cost up to a whole window of resends — more noticeably at 5% than at 1%.
  • The gap widens with the window, and faster at the higher loss rate.
Stay within what we can measure. Our emulator adds delay and loss but has no bandwidth limit, so there is no "bandwidth-delay product" knee in these curves. The proposal's claim is about loss rate and window size, which this experiment tests directly. Do not claim bandwidth effects in the report unless a rate limit is added to the emulator.

13 · Viva preparation

1. Why does Selective Repeat need W ≤ 2k−1 when Go-Back-N only needs W ≤ 2k − 1?
  • Sender window plus receiver window must fit in the sequence space; Go-Back-N's receiver window is 1, Selective Repeat's is W.
  • Draw the k = 2, window 3 failure from 3.4, then the window 2 case working.
2. Why must the receiver ACK packets from the previous window?
  • Delivered packet, lost ACK: the sender cannot advance and keeps resending. Without a fresh ACK it deadlocks.
3. How does the receiver decide whether a packet is new or a retransmission?
  • Its offset from rcv_base: inside the window it may be new or a duplicate of a stored one; in the previous window it is old.
  • This only works because of the window bound.
4. Why a timer per packet? What would a single timer lose?
  • Each loss is recovered independently and in parallel.
  • A single timer on the oldest packet recovers several losses one timeout at a time — the fallback in 3.9.
5. Why Math.floorMod and not %?
  • (1 − 3) % 4 is −2 in Java; floorMod gives 2. Wraparound comparisons break with %.
6. Why a ring buffer rather than a TreeMap?
  • O(1), bounded memory, indexed by a wraparound-safe offset. A TreeMap sorts raw numbers, which misorders packets across a wrap.
7. Four packets, packet 2 lost. Count the retransmissions for each protocol.
  • Walk the timeline in 3.3. Selective Repeat: 1. Go-Back-N: 3.
8. A timer fires for a packet that was already acknowledged. What happens?
  • Nothing is sent: the fire handler checks the packet is still unacknowledged. Explain lazy cancellation.
9. Live change: shrink the window from 32 to 8 during a transfer.
  • The sender stops sending past the new limit; slots already in flight are acknowledged or resent as normal.
  • The receiver's window must match — and the new size must still satisfy the bound.
10. What would SACK blocks change on the wire?
  • sackCount ranges of 32-bit start and end pairs in the payload; the header layout is unchanged.
