3 · Concepts you must master

3.1 · The header, byte by byte

OffsetSizeFieldRules
01versionAlways 1. Reject anything else.
11typeDATA 0, ACK 1, SACK 2, FIN 3, FINACK 4
21flagsBit 0x01 = META, set only on the handshake packet
31reservedWrite 0; ignore when reading
44seqUnsigned 32-bit sequence number
84ackUnsigned 32-bit acknowledgement number (convention 3)
122payloadLenMust equal the bytes that arrived minus 20
142windowUnsigned 16-bit; informational in Core
162checksumRFC 1071, over the header with this field zero, followed by the payload
182sackCount0 in Core; used by Sohini's SACK stretch goal in week 7

Everything is big-endian — network byte order, most significant byte first. ByteBuffer is big-endian by default, so as long as you never call order(ByteOrder.LITTLE_ENDIAN) you get network byte order for free, even though your laptop's processor is little-endian internally.

3.2 · Signed bytes, unsigned fields

Java has no unsigned integers. This is the bug most likely to cost you a day, so understand it before writing a line.

  • A Java byte runs from −128 to 127. The byte 0xF0 reads as −16. Before combining bytes into a larger number, mask each one: b & 0xFF.
  • buf.getInt() returns a signed int. A sequence number of 3,000,000,000 comes back as −1,294,967,296. Widen it with Integer.toUnsignedLong(buf.getInt()) and keep it in a long.
  • Writing is the easy direction: buf.putInt((int) seq) keeps the low 32 bits, which is exactly the bit pattern you want on the wire.
  • The 16-bit fields work the same way with Short.toUnsignedInt(buf.getShort()).
seq on the wire FF FF FF FF buf.getInt() -1 wrong Integer.toUnsignedLong 4294967295 right (PacketTest checks exactly this)

3.3 · The Internet checksum, RFC 1071

  1. Take the datagram — header with the checksum field set to zero, then the payload — as a sequence of 16-bit big-endian words. If the length is odd, the last byte is the high half of a final word.
  2. Add the words using one's complement arithmetic: whenever a sum spills past 16 bits, add the carry back into the bottom. This is the end-around carry.
  3. Take the bitwise complement of the result and keep 16 bits. Write it into offset 16.

Work these by hand before you code, then check each against your implementation:

Example 1 45 00 00 1C 0x4500 + 0x001C = 0x451C complement 0xBAE3 Example 2 FF FF 00 02 0xFFFF + 0x0002 = 0x1_0001 fold: 0x0001 + 0x0001 = 0x0002 complement 0xFFFD Example 3 01 02 03 (odd) 0x0102 + 0x0300 = 0x0402 complement 0xFBFD Example 4 bytes 0..63 word i = 514i + 1, sum = 254,976 = 0x3E400 fold: 0xE400 + 0x3 = 0xE403 complement 0x1BFC (PacketTest)

Verifying on receipt. Either zero the field, recompute, and compare with what arrived — our choice, because it lets the error message show both values — or add every word including the checksum, which gives 0xFFFF for an intact datagram. The guarantee is the same.

What it always catches: any single-bit error. Flipping one bit changes one word by 2j, and 2j is never a multiple of 0xFFFF, so the one's complement sum must change. Flipping one bit of Example 1 to 45 01 00 1C gives 0xBAE2 instead of 0xBAE3.

What it misses: two 16-bit words swapped (00 1C 45 00 still gives 0xBAE3); errors in two words that cancel; and a word changing between 0x0000 and 0xFFFF, which are both zero in one's complement. That is one reason real transports also rely on sequence numbers — a checksum alone does not notice reordering.

3.4 · Stop-and-Wait — rdt 3.0

Only one packet is ever unacknowledged, so the sequence number only needs to answer one question: is this the packet I just had, or the next one? One bit is enough. After the handshake, your data packets are numbered 1, 0, 1, 0 …

Side and stateEventAction
Sender, waiting for ACK bACK b arrives intactStop the timer; next packet uses bit 1−b
TimeoutResend the same packet; restart the timer
Corrupt packet, or ACK for 1−bIgnore it; the timer keeps running
Receiver, expecting bDATA b intactDeliver it, ACK b, now expect 1−b
DATA 1−b intact — a duplicateDo not deliver. ACK 1−b again
Corrupt packetDrop it silently; the sender's timer recovers

Why the receiver must re-ACK duplicates. The data arrives and is delivered, but its ACK is lost. The sender times out and resends. If the receiver discards the duplicate without acknowledging it, the sender resends forever.

Premature timeout. If an ACK is only delayed, the sender resends, then receives both the original ACK and a duplicate. This is why the sender ignores an ACK for the other bit rather than treating it as progress.

The throughput ceiling. One packet per round trip means goodput can never exceed payload × 8 ÷ RTT. With 1400 bytes and a 40 ms RTT that is 280 kbps, however fast the link. That ceiling is a line on Figure 1.

3.5 · The session: handshake, teardown, hash

Handshake. The sender's first packet is DATA with seq 0 and the META flag. Recommended payload: UTF-8 text of three lines — filename, size in bytes, SHA-256 in hex. The receiver rejects a filename containing a line break or a size that does not parse, and replies ACK 0. The META packet can be lost like any other, so the sender retransmits it on timeout and the receiver re-ACKs duplicates.

Teardown. Once the last data packet is acknowledged, the sender sends FIN. The receiver replies FINACK and then lingers for about three timeouts, answering any repeated FIN — because its FINACK can be lost exactly like a data ACK. The sender retransmits FIN on timeout and gives up after a fixed number of tries. Giving up is safe at that point, since the file has already arrived, but it must be logged.

Hash. MessageDigest.getInstance("SHA-256"), updated chunk by chunk — by the sender as it reads the file, by the receiver as it writes chunks in order. Compare the two hex strings at the end and report sha256_match.

Chunking. 8 MiB is 8,388,608 bytes: 5,992 packets of 1400 bytes, the last holding 1,208. Create test files with head -c 8388608 /dev/urandom > test8m.bin in Git Bash or WSL.

4 · Design decisions you must defend

DecisionWhy — the answer to give at the viva
A fixed 20-byte headerConstant-size parsing with no branches, every field at a known offset, and a reserved field for SACK so the format never changes mid-project.
Packet-numbered, not byte-numberedGo-Back-N and Selective Repeat are defined in packets in the textbook, so window arithmetic stays in whole packets. TCP numbers bytes because it streams; we transfer fixed chunks.
Verify the checksum before trusting any fieldA corrupted payloadLen could otherwise drive a read past the end of the buffer or misparse the payload.
Zero-and-recompute verificationSame guarantee as summing to 0xFFFF, but the exception can report both values when they disagree.
Session layer outside the protocolsOne handshake and one teardown for all three protocols: less code, and identical session overhead, so experiments compare only the ARQ logic.
A META flag, not just seq 0In alternating-bit Stop-and-Wait, 0 is also an ordinary data number. The flag makes a late duplicate handshake impossible to mistake for data.
Checksum written as RFC 1071 describes itWe measured 0.6 µs per packet in Java, so there is nothing to gain from optimising it and a lot to gain from being able to explain every line.
Stop-and-Wait times out with the socket, not the timer heapIt only ever has one timer, so a socket receive timeout is the simplest correct tool. From Thu 24 the value comes from Sinjan's estimator.

9 · Experiment 1 — goodput against loss rate

QuestionHow does each protocol's goodput fall as packet loss rises?
VariableLoss 0, 0.1, 0.5, 1, 2, 5, 10, 20%, applied in both directions with --both loss=p

What we expect, and what would be interesting

  • Stop-and-Wait stays under its 280 kbps ceiling at every loss rate, falling as loss rises.
  • Go-Back-N is fastest at 0% but falls steeply, because each loss can cost up to a whole window of resends.
  • Selective Repeat falls gently, because each loss costs one resend.
  • The claim models normalised goodput as roughly (1−p) for Selective Repeat and (1−p)W for Go-Back-N. That model is crude — it ignores ACK loss and the time spent waiting for timeouts — so where the measured curve departs from it, explain why. That analysis is worth more than a curve that happens to fit.

Runtime — plan for it

Stop-and-Wait is the bottleneck of the whole experiment. Estimated at 8 MiB, RTO around 120 ms, loss in both directions: 4 minutes a run at 0% loss, about 11 minutes at 20%. One seed of the eight Stop-and-Wait cells takes about 44 minutes; ten seeds, about 7.3 hours. At 2 MiB those become 1 and 2.7 minutes, and 1.8 hours for ten seeds. So the Stop-and-Wait cells start Friday evening and run overnight. If Sohan's dry run on Tuesday 22 shows they are too slow, the whole experiment — every protocol, not just Stop-and-Wait — moves to 2 MiB, and the report says so. Goodput is a rate, so file size changes the running time, not the number being measured.

13 · Viva preparation

Practise these out loud with a teammate. Sir will also ask you to change code live — the last two are rehearsals.

1. Walk me through the checksum, byte by byte.
  • 16-bit big-endian words; an odd final byte is the high half of a word.
  • One's complement addition with the end-around carry; complement at the end.
  • Computed with the checksum field at zero. Work Example 1 or 2 from 3.3 on the board.
2. Why is every single-bit error caught? Which errors are not?
  • One flipped bit changes one word by 2j, which is never a multiple of 0xFFFF, so the sum changes.
  • Missed: swapped words, errors that cancel, a word flipping between 0x0000 and 0xFFFF.
3. Why Integer.toUnsignedLong on the sequence field?
  • Java's int is signed; above 231 the value reads as negative.
  • Show FF FF FF FF reading as −1 without it and 4,294,967,295 with it.
4. In Stop-and-Wait, an ACK is lost. What happens, step by step?
  • The data was already delivered. The sender's timer fires and it resends.
  • The receiver sees a duplicate, does not deliver it, and ACKs it again. The sender moves on.
5. Why is one bit enough for Stop-and-Wait but not for Go-Back-N?
  • Stop-and-Wait has one packet in flight, so it only distinguishes "this one again" from "the next one".
  • Go-Back-N has up to W in flight, and needs at least W+1 distinct numbers to tell them apart.
6. Why can't Stop-and-Wait go faster than 280 kbps here?
  • One packet per round trip: 1400 × 8 ÷ 0.040 s. The link speed never enters the formula.
7. The FINACK is lost. What happens?
  • The sender's FIN timer fires and it resends FIN; the lingering receiver answers again.
  • If every FINACK is lost the sender gives up after its retry limit — safe, because the file has already arrived.
8. Why verify the checksum before reading the length field?
  • A corrupted length could send the parser past the end of the buffer or mis-split header and payload. Nothing is trusted until the checksum passes.
9. Live change: add a NAK packet type.
  • A new type constant and name; handling in the protocol that sends and receives it; a test.
  • The header layout and the checksum do not change at all — explain why.
10. Live change: make the payload 1000 bytes instead of 1400.
  • It is a ProtocolConfig value, so no header change. More packets per file, and Stop-and-Wait's ceiling drops to 200 kbps.
